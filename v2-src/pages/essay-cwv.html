Shipping Core Web Vitals green: the pre-launch checklist.

Fast sites aren't faster at the end — they're prevented from being slow at the start. This is the checklist I run before every launch, in the order that matters.

Every performance disaster I've inherited had the same shape: performance treated as a launch-weekend activity instead of a contract-time decision. The fixes that actually move the needle — budgets, image pipelines, font strategy — have to happen before the first component is written. Here's the order I do them in, and why.

1. Budget before build

Write numbers down while it's still cheap to change plans: LCP under 1.8 seconds on throttled 4G, CLS under 0.02, total JavaScript under 180 KB compressed for a content site. Then wire those numbers into CI so a pull request that doubles the bundle fails the build. A budget nobody enforces is a wish; a budget in the pipeline is an architecture.

# size-limit, wired into CI
"limits": [
  { "path": "assets/js/**/*.js", "limit": "180 KB" }
]

2. The image pipeline is 80% of the fight

It is still stunning how many "modern" sites ship a multi-megabyte PNG as their hero. The pipeline should be: AVIF first, WebP fallback, PNG last resort; responsive srcset generated at build; width and height on every image so layout never shifts; and a blurred placeholder (LQIP) so images feel instant even before they load. The 2.1 MB hero from this site's first draft now ships as ~100 KB of AVIF — and nobody can tell the difference except the phone on 4G.

3. Fonts: the silent tax

Three families, thirteen weights, no subsetting — the classic portfolio mistake, and I've made it. The fixed version: self-host everything, subset to the glyphs you actually render, preload exactly two critical weights, and use metric-compatible fallbacks so the swap doesn't shift a single pixel of layout. Text should never move after it's painted; on a content site, that's non-negotiable.

4. JavaScript that pays rent

Every kilobyte of JS needs a reason to exist. The site you're reading ships GSAP and Lenis because the motion is the product — and in exchange, the shader hero loads after first paint, animations only run on compositor-friendly properties (transform, opacity, clip-path — never width or top), and every loop suspends when the tab hides. Motion that costs frames is decoration; motion that protects frames is design.

  • Compositor-only animation properties, forever
  • Heavy effects lazy-loaded post-LCP and tier-gated by device capability
  • One animation clock for the whole page, not five rAF loops
  • prefers-reduced-motion as a first-class mode, tested, not assumed

5. Measure where users live

Lab numbers are for catching regressions; field numbers are the truth. Real-user monitoring with attribution — which image, which font, which script caused the slow LCP — turns "the site feels slow sometimes" into "the case-study hero on mobile is the problem, fix that one thing." Sample generously on small sites; the traffic is free and the outliers are the story.

The checklist, compressed

  1. Budgets in CI: JS, CSS, image, per-route weight
  2. AVIF/WebP pipeline with LQIP and intrinsic dimensions everywhere
  3. Self-hosted subsetted fonts, two preloads, metric-matched fallbacks
  4. Compositor-only motion, tiered effects, reduced-motion tested
  5. Field vitals with attribution, reviewed weekly like any other metric

That's the whole religion. None of it is clever — which is the point. Speed is a habit of small disciplined decisions, made early, enforced automatically, and measured where it counts. Green scores aren't the goal; they're the receipt.

Fast is a feature. Ship it like one.
